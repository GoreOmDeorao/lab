# AWS — EC2, User Data, AMIs, and SSH

Practical procedures from Virtualization, Cloud, and AWS slides 15–19 and 57–61.

## 1. Create and use an EC2 key pair

Create or select a key pair while launching an EC2 instance. The slide distinguishes:

- `.pem` for Linux/OpenSSH clients.
- `.ppk` for Windows PuTTY clients.

Keep the private key file secure. Do not upload it to GitHub.

On a Linux machine, restrict its permissions:

```bash
chmod 400 <KEY_PAIR_FILE.pem>
```

SSH to an Ubuntu EC2 instance:

```bash
ssh -i <KEY_PAIR_FILE.pem> ubuntu@<EC2_PUBLIC_IP>
```

For an Amazon Linux EC2 instance:

```bash
ssh -i <KEY_PAIR_FILE.pem> ec2-user@<EC2_PUBLIC_IP>
```

## 2. Ubuntu EC2 user-data script — install Apache

Paste this into the EC2 launch wizard's **Advanced details → User data** field, or save as `userdata.sh` and run it on an Ubuntu EC2 instance.

```bash
#!/bin/bash
set -e

apt update -y
apt install -y openssh-server
systemctl enable --now ssh

ufw allow ssh

apt install -y apache2
systemctl enable --now apache2

ufw allow 'Apache'
ufw --force enable

echo '<h1>Hello World from C-DAC, Pune</h1>' > /var/www/html/index.html
```

Open the EC2 public IP in a browser. Ensure the EC2 security group allows inbound TCP port 80 from the client network.

## 3. Lab — create an EC2 instance with a PRN page

1. Launch an EC2 instance with a public IP.
2. Use the Ubuntu user-data script above, or connect over SSH and install Apache manually.
3. Replace the page with your PRN:

```bash
echo '<h1>PRN - <YOUR_PRN></h1>' | sudo tee /var/www/html/index.html
```

4. Open `http://<EC2_PUBLIC_IP>` and verify the page.

## 4. Create an AMI and launch into another Availability Zone

In the AWS Console:

1. Open **EC2 → Instances** and select the working instance.
2. Choose **Actions → Image and templates → Create image**.
3. Set an image name such as `PRN-AMI` and a description.
4. Create the image.
5. Open **EC2 → AMIs** and wait until the AMI state is **Available**.
6. Select the AMI and choose **Launch instance from AMI**.
7. Select a subnet in a different Availability Zone from the first EC2 instance.
8. Launch the second instance and test both public IPs in the browser.

## 5. Clean up EC2 and AMI resources

After the lab:

1. Stop or terminate both EC2 instances, as required by the lab.
2. Deregister the AMI under **EC2 → AMIs**.
3. Find and delete the snapshot associated with the AMI under **EC2 → Snapshots**.
4. Detach and delete lab-owned EBS volumes under **EC2 → Volumes**.

Check carefully that you are deleting only resources created for the lab.

## 6. SSH from a public EC2 instance to a private EC2 instance

This is the workflow shown in slides 57–61:

1. Launch one EC2 instance in a public subnet and one in a private subnet, using the same key pair.
2. Connect to the public instance using its public IP.
3. Copy the private-key file to the public instance using the transfer method shown in the slides (WinSCP for Windows clients). Do not expose the key publicly.
4. On the public instance, restrict key permissions:

```bash
chmod 400 <KEY_PAIR_FILE.pem>
```

5. SSH from the public instance into the private instance:

```bash
ssh -i <KEY_PAIR_FILE.pem> ec2-user@<PRIVATE_EC2_PRIVATE_IP>
```

## 7. Install Apache on Amazon Linux private EC2

Run on the private instance:

```bash
sudo yum install httpd -y
sudo service httpd start
sudo chkconfig httpd on
curl localhost
```

The source slide includes this DNS workaround only if package installation fails because of name resolution:

```bash
echo "nameserver 8.8.8.8" | sudo tee -a /etc/resolv.conf
```

From the public EC2 instance, test the private web server:

```bash
curl http://<PRIVATE_EC2_PRIVATE_IP>
```

## 8. Stop and clean up the private/public EC2 lab

Delete every resource created for the lab:

- Both EC2 instances.
- Lab subnets and network interfaces.
- Internet Gateway and NAT Gateway.
- Lab Elastic IP allocation.
- Lab VPC.

NAT Gateways and Elastic IP allocations can incur charges while they exist.

Source reference: Virtualization, Cloud, and AWS slides 15–19 and 57–62. The Ubuntu user-data script's invalid `systemctl start ssh -y` was corrected to `systemctl enable --now ssh`.
